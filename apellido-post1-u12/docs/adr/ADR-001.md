# ADR-001: Capas simples para persistencia; el seam de notificacion ya cubre el proximo cambio conocido

## Estado: Aceptado — 2026-10-30

## Contexto
Tras integrar Chain of Responsibility, Strategy y Observer sobre el sistema de solicitudes de reembolso, corresponde
decidir si el proyecto debe migrar a arquitectura Hexagonal completa (puertos e interfaces intermedias para persistencia
y notificacion) o mantenerse en capas simples. La Guia (seccion 6.2) da un criterio: la arquitectura Hexagonal vale la
pena en sistemas que sobreviviran 3 anios o mas con cambios de infraestructura.

Datos del proyecto:
- Persistencia: no existe hoy ningun plan de cambiar el motor de base de datos (H2 en desarrollo, un unico motor
  relacional en produccion). No hay un segundo adaptador que justifique un puerto.
- Notificacion: Contabilidad si anuncio, para el proximo trimestre, una integracion por API externa para el pago de
  solicitudes aprobadas. Es un cambio de infraestructura con fecha conocida.

## Alternativas consideradas
1. **Hexagonal completa** (puerto `RepositorioSolicitudes` + adaptador JPA + puertos de salida de notificacion).
   Descartada para persistencia: sin un segundo motor real seria una abstraccion especulativa (YAGNI) y obligaria a
   agregar una interfaz y un adaptador sin ningun consumidor distinto del actual.
2. **Capas simples en todo** (sin tocar nada en notificacion). Aceptada: `ObservadorCambioEstado` ya es el punto de
   extension que necesita la integracion de Contabilidad.
3. **Hexagonal solo para notificacion** (puerto de salida `PasarelaPagos`). Descartada por ahora: el contrato de la API
   externa aun no existe; disenar el puerto hoy seria adivinar. Se reconsidera cuando Contabilidad entregue el contrato.

## Decision
Se mantiene arquitectura en capas simples para la persistencia: `SolicitudReembolsoService` sigue dependiendo
directamente de `RepositorioSolicitudesJpa`, sin una interfaz de puerto intermedia. Para la notificacion no se
introduce ningun cambio: `ObservadorCambioEstado` ya es el seam necesario, y `NotificadorContabilidad` puede reemplazar su
implementacion interna por una llamada a la API externa el proximo trimestre sin modificar `SolicitudReembolsoService`
ni los demas observadores. Los limites que si existen entre paquetes se protegen con reglas ArchUnit en CI.

## Consecuencias
Positivas:
- No se agregan interfaces ni mappers de persistencia sin un caso de uso real que los justifique.
- El unico cambio de infraestructura con fecha conocida (integracion de Contabilidad) ya tiene su punto de extension listo.
- Menos clases y menos indireccion: el flujo es mas facil de rastrear y depurar.
Negativas:
- Si en el futuro se necesita cambiar de motor de base de datos, el puerto de persistencia debera introducirse
  retroactivamente; se acepta esa deuda tecnica de forma consciente.
- Una llamada sincrona a una API externa dentro de `NotificadorContabilidad` podria afectar la latencia o fallar y
  propagar la excepcion al servicio; el manejo de fallos (reintentos, asincronia) se evaluara al recibir el contrato.
- Un revisor que espere simetria total (puertos en todas las dependencias externas) puede interpretar la asimetria como
  inconsistencia si no lee este ADR.

## Senales para revisar esta decision
- Aparece un segundo motor de base de datos o un requisito de pruebas sin base de datos real.
- El sistema necesita varias integraciones externas con contratos propios (ahi si valen los puertos de salida).
